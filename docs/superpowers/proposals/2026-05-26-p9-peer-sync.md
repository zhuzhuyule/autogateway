# P9: 多实例配置同步 (Peer-to-peer Full Mesh)

> **Status**: 📋 Proposal (待用户拍板 4 个决策点后开 brainstorm → spec → plan → 实施)
> **Author**: zac + Claude
> **Date**: 2026-05-26
> **Tracking task**: #54

## 需求来源 (用户原话)

> 能否做数据同步机制，比如两个或者三个服务器相互联通，A 改了配置，B、C 也会同步，
> 同理 B 改了，A、C 同步。同步服务器需要 IP/域名和密钥，可以看到和哪些站点同步了、
> 同步时间、差异等？

## 推荐架构

**Peer-to-peer full mesh** —— n 个节点互联，任一节点改配置异步 push 到所有 peers + 定时 pull 兜底。

```
┌──────────┐  push on change   ┌──────────┐
│  Node A  │ ←────────────────→ │  Node B  │
└──────────┘  pull every 5min  └──────────┘
       ↘                              ↗
        ↘     ┌──────────┐         ↙
         ────→│  Node C  │←────────
              └──────────┘
```

### 设计选择（务实最简版）

| 维度 | 推荐 | 理由 |
|---|---|---|
| 拓扑 | full mesh (peer-to-peer) | 任一节点都能写, 单点故障不影响 |
| 传输 | HTTP POST `/api/sync/push` `/pull` | 不引入 WebSocket/gRPC 依赖 |
| 序列化 | 复用 `backup` `.acb` 格式 | 已有加密 + 完整 schema, 0 新代码 |
| 触发 | 配置变更后 async push + 5 min pull 兜底 | 实时性 + 可靠性兼顾 |
| 冲突解决 | **last-write-wins** (按 `updated_at`) | MVP 简单, 多人冲突场景罕见 |
| 鉴权 | 共享 `SyncKey` + HMAC 签名 + HTTPS | 跟 AUTH_KEY 隔离避免泄露管理面 |

## 同步范围

| 表 | 默认 | 备注 |
|---|---|---|
| `groups` / `sub_groups` | ✅ 同步 | 核心配置 |
| `aliases` / `exposed_models` | ✅ 同步 | 智能路由 |
| `system_settings` | ✅ 同步 | 全局设置 |
| `api_keys` | ❌ **默认排除** | 含敏感数据, 用户可在 UI 勾选启用 |
| `request_logs` | ❌ 不同步 | 大数据量, 各节点本地累积 |
| `free_models_cache` | ❌ 不同步 | 各节点本地从 ofind.cn 拉 |

## 4 个待拍板决策点

开始 brainstorm + spec 前需要用户确认：

### 1. 拓扑规模
- A. 2-3 台 (small mesh, push 给所有 peers 成本 O(n))
- B. 5+ 台 (考虑 hub-spoke 或分区, push 成本 O(n) 可能高)
- C. ≥ 10 台 (需要分布式架构如 Raft, 超出 MVP 范围)

### 2. API keys 同步策略
- A. 默认排除 (推荐, 安全考量) — 用户在 UI 勾选启用
- B. 默认包含 — 用同步密钥加密传输
- C. 不可配置, 永远排除

### 3. 冲突解决
- A. last-write-wins 自动覆盖 (推荐, MVP) — 按 updated_at, 后改的赢
- B. 冲突时暂停同步 + UI 提示人工 resolve
- C. 版本号 / CRDT 全自动合并 (复杂度高, 不推荐 MVP)

### 4. 实时性
- A. 变更后立刻 async push (秒级延迟) + 5min pull 兜底 (推荐)
- B. 仅 push, 不 pull (变更必须同步成功才认完成)
- C. 仅定时 pull (分钟级延迟, 实现最简)

## 不在 MVP 范围

- 双向带宽限速 / QoS
- 增量 diff (MVP 直接全量 push payload)
- Audit log / 同步历史回溯
- 多租户 / 权限隔离
- 跨数据中心 (假设节点都在同一 LAN/VPN, 网络可靠)
- Schema migration 同步 (不同版本 peer 之间的协议兼容)

## 风险点

1. **冲突频率**：多人同时改 → last-write-wins 可能丢失改动. MVP 假设单管理员或低并发.
2. **网络分区**：partition 期间各节点独立改 → 合并时旧版本被覆盖. 需要日志记录方便复盘.
3. **api_keys 同步安全**：若用户启用 keys 同步, 传输 + 存储必须强加密, peer 任一被攻破 = 所有 keys 泄露.
4. **schema 版本不一致**：v2.4.10 vs v2.5.0 peer 之间 payload 字段可能不兼容. 需要 schema version 字段 + 渐进迁移策略.
5. **环形 push 风暴**：A push → B 触发 hook → push 回 A → loop. 需要 "origin tag" 防回环.

## 与现有功能的关系

- **复用 backup 基础设施**：序列化 (`.acb` 格式) + 加密 (Argon2id + AES-GCM) + schema validation 全部已有, P9 只是把 backup 的 export/import 流程网络化.
- **不影响现有 routing**：sync 是控制面, 不影响数据面 (proxy /v1/chat/completions).
- **跟 free_models registry 互补**:
  - free_models cache 是各节点本地 6h 拉 ofind CDN, 不需要 sync
  - peer sync 是 admin 配置 (groups/aliases) 在节点间一致
